# ЛР 4 · Стратегия split, черновик разметки и план B

**Проект:** CineMatch · **Версия:** 1.0 · **Состояние:** план зафиксирован; реальный CSV пока не проходил запуск проверки. См. [Data Card](data_card.md).

## 1. Для чего разделяются выборки

Оценивается **персональное ранжирование для существующего пользователя**: на основе ранних оценок предлагать фильмы, которые ему понравятся позднее. Поэтому правильная единица split — **взаимодействия одного пользователя в порядке времени**, а не случайная строка без учёта связи.

| Выборка | Примерная доля на пользователя | Назначение | Какие метки доступны |
|---|---:|---|---|
| Train | первые ~60% временных групп | построение профиля, baseline, fit TF-IDF, подбор статистик | только train |
| Validation | следующие ~20% | выбор варианта модели и параметров, без fit на val | только проверка |
| Test | последние ~20% | однократная финальная оценка | не доступны до фиксации модели |

**Связанная группа:** все оценки одного пользователя с одинаковым `timestamp` (например, выставленные пакетно) целиком в одном split. Повторные пары `(userId,movieId)` разрешаются до разбиения с документированием правил, чтобы одна пара не встречалась в разных частях. Пользователей с менее чем тремя уникальными временными группами выделить как `not_evaluable`, не заявляя оценку cold start. Следует учитывать, что точность временных меток ограничена.

**Не применяется групповое исключение по `userId`:** полное разделение пользователей проверяло бы другую задачу — рекомендации для новых пользователей, у которых нет истории. Её необходимо оценивать отдельным исследованием.

## 2. Проверки против утечки

1. Сортировать по `userId, timestamp, movieId`, сохранить журнал преобразований и хеши исходных файлов.
2. Удалить/разрешить повторные `(userId,movieId)` по заранее объявленному правилу; иначе возможны дубли между частями.
3. Для пользователя выделить уникальные временные группы и назначить первым 60% train, следующим 20% validation, последним ~20% test; для малого числа групп гарантировать минимум одну группу в каждом split.
4. Проверить `set(train(userId,timestamp)) ∩ set(validation(...)) = ∅` и все другие попарные пересечения; аналогично для пар `(userId,movieId)`.
5. Проверить строгую временную последовательность `max(train.timestamp) < min(validation.timestamp) < min(test.timestamp)` для каждого пригодного пользователя.
6. До test зафиксировать TF-IDF/IDF по жанрам кандидатов, участвовавших в train; популярность фильмов вычислять **только из train**. Отложенные оценки не должны влиять на пользовательские профили. Если используются теги, не допускать `tags.timestamp` позднее момента рекомендации.
7. Validation применяется к настройке метода; test — один раз к финальному выбору. На реальных пользовательских данных потребуется независимое проспективное тестирование.

**Проверяемый скрипт:** [validate_split.py](validate_split.py) запускается на скачанном `ratings.csv`, создаёт отчёт и утверждения `assert`. Команда: `python validate_split.py /path/to/ml-latest-small/ratings.csv`. При отсутствии CSV можно выполнить отдельную искусственную smoke-проверку `python validate_split.py --self-test` — это **не** проверка оригинального набора.

**Важное допущение:** все фильмы из каталога рассматриваются как известные в момент рекомендаций, хотя дата добавления `movieId` в MovieLens неизвестна. Это оставляет риск исторической утечки каталога; эксперименты не следует интерпретировать как точную симуляцию сервиса в прошлые годы.

## 3. Черновик инструкции разметки релевантности

**Кто размечает:** для офлайн-эксперимента правило фиксируется автоматически из предоставленной пользователем оценки, а не выводится из жанра. Правило применяется одинаково во всех выборках.

| Метка | Условие | Смысл |
|---|---|---|
| 2 — высокая релевантность | `rating >= 4.0` | пользователь явно положительно оценил фильм |
| 1 — частичная | `3.0 <= rating < 4.0` | средняя оценка |
| 0 — низкая | `rating < 3.0` | отрицательная/низкая оценка |
| NA — не размечено | оценки нет | неизвестный интерес, **не 0** |

Для NDCG@10 использовать градуированную шкалу и фиксированную трактовку отсутствующих оценок как `unjudged`; публиковать покрытие наблюдаемых релевантных объектов. Для HitRate@10 релевантными считаются `rating >= 4` по holdout. Сегменты без релевантных объектов оговаривать отдельно. Не выбирать границы меток после просмотра test.

**Будущий ручной опрос:** независимые участники могут оценить Top-10 по шкале 0–2 с правилом «0 — не подходит, 1 — частично подходит, 2 — хотел(а) бы посмотреть». Размечать без знания названия алгоритма, по крайней мере два оценщика для спорных случаев. Это **план**, а не проведённое исследование.

## 4. План B

**Если MovieLens недоступен по сети:** использовать только оригинальный архив, полученный законно ранее и проверенный по зафиксированной контрольной сумме; если такого нет — не выдавать подмену за MovieLens.

**Если выяснится, что права не покрывают конкретный сценарий:** остановить соответствующую обработку, уточнить разрешение либо использовать собственные оригинальные учебные карточки. В синтетическом контуре планируется до 36 макетов с полями `id`, `genre`, `description`, `creator_group`, `series_group`, `synthetic=true`, `rights_status=demo_allowed`, `sha256`. Создание и фактический объём пока **не подтверждены**; на реальных постерах, персонажах и логотипах не обучаться.

**Для технической проверки:** создавать разные `creator_group`/`series_group` для train/validation/test, отделять группы целиком и не допускать пересечения хешей. При необходимости смоделировать 3 дубликата, 2 неизвестных разрешения и 1 пустое описание, документировать исключения. Все выводы ограничить корректностью очистки и маршрута данных; никакого доказательства рыночной полезности или качества настоящих рекомендаций.

**При отказе от дополнительных тегов/постеров:** достаточно жанров и оценок MovieLens; приложение может показывать текстовые карточки без заимствованных изображений.
